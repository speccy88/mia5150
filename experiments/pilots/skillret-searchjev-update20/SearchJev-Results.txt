SearchJev-0.8B continued training on SkillRet
2026-10-06

Completed a 20-optimizer-update pilot on the RTX 2060 SUPER. This continued the released SearchJev rank-16 adapter; it did not initialize a new LoRA or train the full base model. The trained adapter and raw evidence are saved. The PC has been released.

The pilot establishes that this small training configuration works on SM75 with the stock PyTorch fallback and dynamic FP16 loss scaling. It does not establish a useful quality improvement. Keep the released baseline as the reference; the adapted checkpoint is experimental. The 200-update expansion was not run because the development objective and calibration worsened.

Fixed development comparison (60 balanced query-skill pairs from 16 queries):

Four errors became correct; three correct answers became errors. The accuracy gain is only one pair. Query-cluster bootstrap 95% intervals for adapted-minus-baseline differences were -4.35 to +6.76 percentage points for accuracy and +0.0104 to +0.7906 for the combined loss. These intervals condition on this small, exposed sample and do not demonstrate unseen-data generalization.

Data and evaluation limits:
- Verified the official local SkillRet revision 6583d7d2ed07644d0fb8938ed8178f3a7dc42a12: 63,259 training queries, 10,123 training skills, and 127,190 positive edges. Every query's skill IDs matched its qrels.
- Selected 32 eligible training queries, preserving all 33 positive edges, plus 33 deterministic non-gold negatives. Twenty updates used 160 presentations of these 66 unique pairs, about 2.42 passes.
- The evaluation retained all 30 gold edges for 16 development queries plus 30 negatives. Every official gold edge for each selected query was excluded from its negative candidates.
- Repository/name families were recomputed across both train and test catalogs. This found a bridge in the older split. The new selection has zero family overlap between actual training and evaluation candidates, including negatives.
- All 4,392 public test queries and existing development panels are already exposed. Exact IDs for an older 256-example development set at another revision were unavailable. No blind holdout claim is made.
- This is a gold-conditioned binary relevance diagnostic with random negatives, not a full-corpus retrieval benchmark. Skill bodies were not used. At the 256-token limit, 35/66 training query texts and 36/60 evaluation query texts were truncated; 16/66 training and 9/60 evaluation skill headers were truncated.

Training and correctness:
- Batch 1; maximum 256 tokens; left padding to a multiple of 128; gradient accumulation 8; workers 0; one CPU thread.
- Unfused AdamW, learning rate 1e-5, weight decay 0.01, gradient clipping 1. Non-reentrant gradient checkpointing; cache disabled.
- FP16 autocast; FP32 adapter parameters and option loss; GradScaler initially 128. Final-position A/B logits use token IDs 32/33 with A=Relevant, B=Not relevant, temperature 1.
- Exact released-adapter tensor equality was checked before training. Only 10,822,656 LoRA parameters were trainable.
- The first two updates had finite, nonzero gradients and changed all 372 adapter tensors. Full frozen-base hashes were unchanged.
- Saving and loading the same adapter produced identical tensors and zero maximum logit difference on four fixed examples. An independent fresh-process full-base reload also passed.
- The final run encountered one overflow in six first-layer DeltaNet adapter gradient tensors before update 6. GradScaler skipped the unsafe step; hashes proved the adapter was unchanged. The same batch and RNG state passed at scale 64. All 20 applied updates had finite, nonzero gradients.
- The final frozen base remained unchanged. An independent saved-file check confirmed 372 finite FP32 tensors in the 43,340,856-byte adapter.
- Earlier attempts remain in the audit trail: an initial same-process full-base reload stopped on a swap event, a cross-run bitwise training comparison was too strict, and a later attempt stopped on a combined gradient assertion before dynamic overflow recovery was added. These independent attempts are not summed into one training trajectory.

Measured feasibility for the successful run:
- Twenty optimizer updates: 211.65 seconds including the overflow retry; mean 10.58 seconds/update.
- Training, validation and final evaluation span: 247.80 seconds. Entire guarded run: 294.77 seconds.
- A linear 200-update compute-only estimate is 35.3 minutes at these settings. That duration was not tested and excludes setup/evaluation overhead.
- Peak total GPU memory: 1,885 MiB; peak temperature: 59 C. Torch peak allocated/reserved: 1,704/1,758 MiB.
- Minimum host/guest available RAM: 3.23/3.63 GiB. Maximum host CPU: 75.90%. No active guest swap in the successful run; host telemetry age stayed below 1.02 seconds.
- USE_HUB_KERNELS=NO was set before imports; fla and causal_conv1d were absent. No extra kernels, environment upgrades, private uploads, telemetry, paid calls or system-setting changes were used.
- Host paging activity was not measured by the reused monitor; the no-active-swap assertion uses Linux pswpin/pswpout counters.
